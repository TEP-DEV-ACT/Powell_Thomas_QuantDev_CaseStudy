### Architecture and data model — what you built and why

I built the application as a layered data platform rather than putting the logic directly into the dashboard. The ingestion layer pulls SEC EDGAR XBRL facts and 10-K filings, Yahoo Finance price data, and FRED macroeconomic data into PostgreSQL; the transform layer normalises the inconsistent SEC data into a clean annual fundamentals dataset; and the metrics layer contains deterministic calculations for reported, derived and valuation metrics. The core model separates raw `xbrl_facts` from the normalised `fundamentals`, with separate tables for `prices`, `filings`, filing sections/chunks, macro observations and ingestion provenance. I chose this structure because it gives me an auditable source of truth, makes re-ingestion idempotent, and keeps the web and AI layers completely separate from data acquisition. It also means the dashboard can run from the committed seed snapshot without requiring live external data.

### How you integrated the three sources, especially the cross-source join

The three primary sources are integrated into a common PostgreSQL model using ticker/company identity as the main key and fiscal dates as the temporal context. SEC provides the reported fundamentals and filing narrative, Yahoo Finance provides daily market prices, and FRED provides the macro capex cycle. The key cross-source join is between the latest annual SEC fundamentals record and the latest market-price observation for the same ticker: this allows the application to calculate trailing P/E as latest price divided by latest reported diluted EPS, and P/S using market capitalisation divided by reported revenue. I deliberately expose both the fundamental and price as-of dates so the user can see that the market price is current while the accounting data may be several months old. FRED is then joined at the analytical layer rather than being forced into the company financial model, allowing company capex growth to be compared with the national capex cycle.

### Where you used the LLM, where you deliberately didn't, and the reasoning

I used Claude as a tool-use agent specifically for the natural-language Q&A layer, rather than making it part of the underlying data pipeline. The agent has five typed tools covering fundamentals, company comparisons, valuation, filing search and capex context, allowing it to decide whether a question requires structured financial data, filing narrative, or both. For example, a question about Microsoft's revenue growth and management's explanation causes the model to call both the fundamentals and filing-search tools, with the tool trace exposed to the user as a grounding audit trail. I deliberately did not use the LLM for ingestion, SEC parsing, arithmetic, charts or tables: those operations are deterministic because introducing an LLM into the data path would create unnecessary hallucination and reproducibility risks. The model therefore interprets and communicates retrieved information, while SQL/Python remains responsible for the actual numbers.

### Choice of backend, UI framework and data persistence technology

I chose Flask with Jinja and vanilla JavaScript for both the backend and UI, rather than Streamlit, because the case study benefited from having direct control over the dashboard layout and interaction model. Flask serves both the HTML dashboard and `/api/*` JSON endpoints, keeping the architecture to a single lightweight application process rather than introducing unnecessary services for a relatively small internal analytical tool.  I have built a very similar app at my last job using flask and pulling data from Databricks so I was confident on this approach. PostgreSQL was chosen as the persistence layer because it provides a robust relational model for the financial data and, importantly, gives me PostgreSQL full-text search through `tsvector` and a GIN index for the 10-K narrative without requiring a separate vector database or embedding provider. Plotly is loaded via CDN for the interactive charts, avoiding a frontend build pipeline while still providing useful zooming, hovering and download functionality.

### Additional analytical metric — what it is, why you picked it, and what it tells an investor

My additional metric is the **Capex Cycle Beta**, supported by **Capex Intensity**. Capex intensity measures capital expenditure as a percentage of revenue, showing how much of each revenue dollar a company is reinvesting into physical or computing capacity. Capex Cycle Beta goes a step further by comparing the company's year-on-year capex growth with the year-on-year growth of the national private non-residential investment capex series from FRED. I chose it because the investment thesis behind the universe is heavily connected to the AI and infrastructure capex cycle: Microsoft and Google are major spenders, while Nvidia and Eaton are suppliers into that spending cycle, with Apple acting as a useful control. The metric therefore helps distinguish simply *high* capex from capex that is accelerating relative to the wider economy, which can give an investor an indication of whether a company may be early or late in the capital-spending cycle.

### Adjusted net income — tag selection and tax-effecting tradeoff

`adjusted_net_income` backs the reported "Other income (expense), net" line out of net income, so a one-off investment mark-to-market or equity-method gain/loss doesn't read as a change in operating performance. Two tradeoffs are worth being explicit about. First, tag selection: EDGAR filers tag this line inconsistently, and I prefer the aggregate "Other income (expense), net" income-statement subtotal (`NonoperatingIncomeExpense`, falling back to `OtherNonoperatingIncomeExpense`) over the narrower ASC 321 mark-to-market note tag (`EquitySecuritiesFvNiUnrealizedGainLoss`) even when a company reports both — the narrow tag looked more surgical on paper, but in practice materially understates the real swing (e.g. it captures only a fraction of GOOGL's FY2025 non-operating income and misses MSFT's OpenAI equity-method losses entirely). The aggregate line matches each company's actual reported story, at the cost of also bundling in interest income/expense for filers that don't tag it separately — a known precision gap, not a pure investment-marks isolate. Second, tax treatment: the reported non-operating line is pre-tax, while net income is after-tax, so the adjustment is tax-effected using the company's own effective tax rate for the year (`income_tax_expense / (net_income + income_tax_expense)`) rather than subtracted whole or at a flat assumed rate — closer to how "core earnings" adjustments are typically presented, without requiring a further, separately-tagged split of interest income from the equity/investment component.

### Key tradeoffs and what you deliberately left out given the time box

The main tradeoff was choosing breadth and a robust end-to-end architecture over building a much more sophisticated research platform. Within the roughly 8–10 hour time box, I prioritised reliable ingestion, normalisation, cross-source joins, a usable dashboard and a grounded AI interface rather than adding features such as analyst estimates, forward guidance, price targets, portfolio construction, forecasting models or a full vector/semantic retrieval system. I also chose lexical PostgreSQL full-text search rather than embeddings, avoiding another external dependency and making the system easier to reproduce for a grader. Similarly, I kept the backend as a single Flask service rather than splitting it into microservices, and used seeded data so the application remains runnable without live network access. These are deliberate scope decisions: the objective was to demonstrate sound quantitative engineering and product judgement rather than maximise the number of features.
